# Техническое задание (переработанное) — SEO-платформа «PF»

Версия документа: 1.0
Статус: утверждено к реализации (см. [ROADMAP.md](ROADMAP.md))

---

## 0. Важное замечание о смене предметной области

Исходное ТЗ описывало сервис накрутки поведенческих факторов в Яндексе (эмуляция кликов
реальных пользователей, обход капчи, антидетект, пул чужих аккаунтов). Такой сервис
нарушает пользовательские соглашения Яндекса и относится к манипуляции чужой
инфраструктурой, поэтому он не реализуется.

Вместо него реализуется **легитимная SEO- и аналитическая платформа**, которая
переиспользует ~80% исходного пользовательского интерфейса и модели данных:
проекты, ключевые слова, регионы, расписание, очередь задач, статистика, биллинг
через ЮKassa, личный кабинет, админ-панель.

| Было в исходном ТЗ | Стало в переработанном ТЗ |
| --- | --- |
| Бот кликает по выдаче Яндекса | Сборщик снимает **позиции** домена по ключу (официальные API / Яндекс XML) |
| Имитация поведения на чужом сайте | **Аналитика воронки** и A/B-тесты **на своих сайтах** (Метрика/GA4 API) |
| Пул «прогретых» Яндекс-аккаунтов | Пул **API-ключей** (Яндекс XML, Wordstat, GSC) с учётом лимитов |
| Обход капчи нейросетью | Нейросеть для **кластеризации ключей**, генерации ТЗ на контент, разбора аудита |
| Прокси-ротация для антидетекта | Нет. Только легальные rate-limit-очереди |
| Режим «конверсия» (заполнение чужих форм) | **Нагрузочное и e2e-тестирование своих** сайтов на Playwright |

## 1. Общее описание

PF — внутренний инструмент компании для SEO-специалистов. Пользователь создаёт проект
(сайт), задаёт ключевые слова, регионы и расписание съёма. Планировщик по расписанию
ставит задачи в очередь, воркеры снимают позиции и частотности, платформа хранит историю
и строит отчёты. Дополнительно доступны технический аудит сайта, аналитика конверсий и
A/B-тесты на собственных ресурсах.

## 2. Роли

- **Пользователь (SEO-специалист)** — проекты, ключи, отчёты, баланс.
- **Администратор** — API-ключи и квоты, пул воркеров, мониторинг очереди, тарифы, пользователи.

## 3. Личный кабинет

### 3.1. Регистрация и аутентификация
- Регистрация по email/паролю, подтверждение письмом (токен, TTL 24 ч).
- Вход, JWT access (15 мин) + refresh (30 дней, httpOnly cookie).
- Опционально: 2FA (TOTP).
- После входа — раздел «Мои проекты».

### 3.2. «Мои проекты»
Список: название, домен, статус (вкл/выкл), число ключей, дата создания, средняя позиция.

Создание проекта:
- Название (произвольное).
- Ссылка на сайт (основной домен, напр. `analitika-marketpleysov.ru`).
- Поисковая система: Яндекс / Google / обе.
- Подтверждение владения доменом (DNS TXT либо HTML-файл) — **обязательно** для
  аудита, аналитики и A/B-тестов; для съёма публичных позиций — необязательно.

Вкладки проекта: **Ключевые слова**, **Регионы**, **Расписание**, **Аудит**,
**Аналитика**, **Дополнительно** (вкл/выкл проекта, удаление).

#### 3.2.1. Ключевые слова
- Ручной ввод + кнопка «Добавить».
- Массовый ввод: текстовое поле, ключи через Enter.
- Импорт Excel/CSV. Колонки: `keyword, tag, interval_min, target_url, region`.
  (`tag` — бывшая «подсказка»: используется как метка группы/уточнение запроса.)
- В таблице по каждому ключу: редактировать, удалить, задать тег, интервал съёма (мин),
  целевой URL (если пуст — главная домена), регион(ы), приоритет.
- Хранение на сервере с привязкой к проекту; уникальность `(project_id, keyword, region_id)`.

#### 3.2.2. Регионы
- По умолчанию: Москва (213), Санкт-Петербург (2), Самара (51).
- Мультивыбор; справочник регионов расширяем администратором.
- Регион передаётся параметром `lr` в официальный поисковый API — без эмуляции IP.

#### 3.2.3. Расписание
- Дни недели (пн–вс) — чекбоксы.
- Окно работы (напр. 09:00–21:00) с таймзоной проекта.
- Глобальный рубильник «Включить/Выключить проект»: при выключении задачи не ставятся в очередь.
- Минимальный интервал съёма по одному ключу — 60 мин (защита от превышения квот).

### 3.3. «Очередь задач»
Колонки: ID задачи, ID проекта, домен, тип (`position` / `wordstat` / `audit` / `ab_test`),
подзадач, в очереди, в процессе, завершено, ошибка, не найдено, отменено, создан, обработан.

- Клик по строке — детальный статус: лог этапов, HTTP-коды, сырой ответ API (для админа),
  снятые позиции.
- Пагинация, фильтры по статусу/проекту/типу/датам.
- Статусы: `queued → running → done | not_found | error | cancelled`.
- `not_found` — домен отсутствует в топ-100 выдачи по ключу.

### 3.4. «Статистика»
- Графики: динамика средней позиции, распределение по топ-3/топ-10/топ-50/топ-100,
  видимость (visibility index), число успешных/ошибочных съёмов.
- История позиций по каждому ключу по дням (таблица + график, сравнение периодов).
- Частотность запросов через API Яндекс.Wordstat (базовая/«точная»/фразовая), кэш 30 дней.
- Аналитика конверсий своих сайтов через API Яндекс.Метрики / GA4: воронки, источники, цели.
- Экспорт: CSV, XLSX, PDF-отчёт; отправка отчёта на email по расписанию.

### 3.5. «Профиль»
- Баланс, кнопка «Пополнить» → ЮKassa (тестовый режим на MVP), возврат по webhook.
- История платежей и списаний (детализация по типам задач).
- Настройки: смена пароля, email, таймзона, уведомления.

## 4. Логика работы воркеров

### 4.1. Съём позиций (`position`)
1. Планировщик (cron, шаг 1 мин) выбирает ключи, у которых
   `now >= last_run + interval` и текущее время попадает в окно расписания, проект включён,
   баланс > 0. Создаёт задачи (идемпотентно, по ключу `project_id:keyword_id:region:date_hour`).
2. Воркер берёт задачу, берёт API-ключ из пула с учётом квоты (Redis token bucket).
3. Запрашивает выдачу (Яндекс XML API / Google Custom Search) c параметрами
   `query = keyword`, `lr = region`, глубина до 100 результатов.
4. Ищет в результатах целевой домен (сравнение по eTLD+1, с учётом поддоменов по настройке).
5. Найден → сохраняет `position`, `found_url`, `serp_snapshot`; не найден → `not_found`.
6. Списывает стоимость задачи с баланса, пишет транзакцию.
7. Ошибка сети/квоты → ретрай с экспоненциальной задержкой (3 попытки), затем `error`.

### 4.2. Частотность (`wordstat`)
Раз в 30 дней на ключ: запрос в Wordstat API, сохранение `frequency_base`,
`frequency_exact`, `frequency_quoted`.

### 4.3. Технический аудит (`audit`)
Только для доменов с подтверждённым владением. Краулер (respect `robots.txt`, лимит RPS,
свой User-Agent `PF-Audit/1.0`) собирает: коды ответов, title/description/h1, дубли,
битые ссылки, canonical, редиректы, вес страницы, Core Web Vitals (Lighthouse).

### 4.4. A/B-тесты и e2e (`ab_test`)
Playwright сценарии **на своих сайтах**: прохождение воронки, проверка форм, измерение
времени загрузки, скриншот-регресс. Никакой маскировки автоматизации — обычный headless.

## 5. Админ-панель
- **API-ключи и квоты**: Яндекс XML, Wordstat, GSC, Метрика, OpenAI-совместимый LLM.
  Лимиты в сутки/час, счётчики расхода, алерты при 80% квоты.
- **Воркеры**: список, heartbeat, нагрузка, ручной рестарт.
- **Очередь**: просмотр задач всех пользователей, отмена, повторный запуск, логи.
- **Пользователи и тарифы**: пакеты съёмов, ручная корректировка баланса, блокировка.
- **Справочники**: регионы, поисковые системы, типы задач.
- **LLM-интеграция**: кластеризация семантики, генерация ТЗ на тексты, объяснение
  результатов аудита. Настройка эндпоинта, модели, «уровня интеллекта» (temperature/бюджет токенов).

## 6. Стек

- **Backend**: NestJS (TypeScript), PostgreSQL 16, Redis 7, BullMQ.
- **Frontend**: React + Vite + TypeScript, Ant Design. Для GitHub Pages — статическая сборка.
- **Воркеры**: Node.js, Playwright (аудит/e2e), HTTP-клиенты к официальным API.
- **Инфраструктура**: Docker Compose (dev), Kubernetes (prod), GitHub Actions CI/CD.
- **Наблюдаемость**: Prometheus + Grafana, Sentry, структурные логи (pino).

## 7. Безопасность
- Пароли — argon2id. Секреты и API-ключи — шифрование AES-256-GCM ключом из KMS/переменной окружения.
- RBAC (user/admin), rate limiting на API, CSRF на cookie-сессии, CSP.
- Баланс не уходит в минус: списание в одной транзакции с `SELECT ... FOR UPDATE`;
  при нулевом балансе постановка задач блокируется.
- Аудит-лог действий администратора.
- Соблюдение robots.txt и rate limit при краулинге; работа только с подтверждёнными доменами.
- Персональные данные — по 152-ФЗ; хранение в РФ-регионе.

## 8. Нефункциональные требования
- Съём до 100 000 позиций в сутки при 10 воркерах.
- p95 ответа API < 300 мс.
- Хранение истории позиций — не менее 24 месяцев.
- Доступность 99,5%, ежедневный бэкап БД, RPO 24 ч.

## 9. Демо на GitHub Pages
Ограничение: GitHub Pages отдаёт только статику, backend там работать не может.
Поэтому в Pages публикуется **демо личного кабинета** (`app/`) с локальным хранилищем
(`localStorage`) и детерминированными демо-данными. Инструкция — [DEPLOY-GITHUB-PAGES.md](DEPLOY-GITHUB-PAGES.md).
